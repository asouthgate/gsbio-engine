# `@catshark/react-ui`

Headless **presentational** components that project the engine's slices
into the canonical draw → configure → run workflow. Sibling package to
`@catshark/react`; lets the engine ship the workflow scaffolding once
instead of having every domain app re-author it.

## What lives here

Six thin components, each a 1:1 projection of an engine slice. They call
hooks already defined in `@catshark/react` and introspect model/data-source
registries in `@catshark/core`. Nothing here contains simulation logic,
rendering-backend code, or shipped CSS.

| Component | Projections | Notes |
| --- | --- | --- |
| `<DrawToolbar>` | `draw.drawMode` + `draw.pendingCategory` | 5 modes incl. `circle`; `tools` prop subsets/relabels/combines |
| `<ModelForm>` | `model` slice + `listModels()`/`getModel()` + `ModelParamDef` | drives `SET_MODEL` / `SET_PARAM`; schema-only (no run button) |
| `<RunPanel>` | `run` slice (current run) | run button with sliding-hash overlay + cancel + inline progress + error |
| `<ResultsPanel>` | `run` slice (history) | list of completed runs; per-row "Show on map" toggle (add/remove ResultLayer) + clear |
| `<FeatureList>` | `sources` + `draw.features` | source-grouped, per-feature edit/visibility/remove; collapsible per-kind geometry inspector |
| `<MapScene>` | `<Canvas>` + positions an overlay context | renderer/tiles stay domain-supplied via the `renderer` prop |

## Imports

```tsx
import { DrawToolbar, ModelForm, RunPanel, ResultsPanel, FeatureList, MapScene } from '@catshark/react-ui';
```

## `<DrawToolbar>` — configurable toolset

```tsx
import type { ReactNode } from 'react';

export interface DrawTool {
  mode: DrawMode;   // 'select' | 'point' | 'linestring' | 'polygon' | 'circle'
  label: string;
  icon?: ReactNode;  // string (emoji), <SVG/> component, … ; falls back to a default glyph
}

export interface DrawToolbarProps {
  className?: string;
  tools?: readonly DrawTool[];  // defaults to all five modes with default labels
}
```

- Set of `DrawMode`s is **closed** — the engine owns growth of the union
  (`select` / `point` / `linestring` / `polygon` / `circle` today). Domain
  apps cannot invent new modes; they can only pick a subset.
- The `label` on each tool flows through to the **feature's `category`**
  the moment a feature is drawn. Two tools may share a `mode` with
  different labels (the canonical case: a "Roost" and a "Light Source"
  tool, both drawing circles). Features are later retrievable by category
  via `featuresByCategory(features, 'Roost')` from `@catshark/core`.
  The category is **read-only** in the feature panel — it is set by the
  tool that created the feature and cannot be re-typed from the panel.
  Additional labels/categories will be added as a separate feature later.
- The `icon` is optional and **anything renderable** — a string for a
  quick glyph ("💡"), or an inline SVG / icon component for a professional
  domain look. Omit to keep the engine default glyph for `mode`. Two
  same-mode tools should set different icons (or different labels) so
  they remain glance-distinct.
- The active button is identified by matching **both** `mode` and
  `pendingCategory`, so two same-mode tools never appear active together.
- Default: `<DrawToolbar />` renders all five modes with labels
  `Select / Point / Line / Polygon / Circle`.

```tsx
<DrawToolbar tools={[
  { mode: 'select', label: 'Select' },
  { mode: 'circle', label: 'Roost' },
  { mode: 'circle', label: 'Light Source' },
]} />
```

## Circles as semantic geometry

GeoJSON has no Circle type, so a drawn circle is stored as **two views of
the same feature**:

- `feature.circle = { center: LngLat, radiusMeters: number }` — the
  **semantic truth**, used by any `ComputeProvider.preprocess` (e.g. "is
  observation *X* inside the roost exclusion zone?" via `pointInCircle(obs,
  circle.center, circle.radiusMeters)`).
- `feature.geojson` — a `Polygon` approximation (great-circle sampling,
  64 segments by default) used purely for **rendering**.

The polygon is regenerated by the engine when the center or radius is
edited from the side panel (`updateCircle(id, { center?, radiusMeters? })`);
the renderer picks up the new geometry via `DrawMapActions.updateFeatureGeometry`.

**Circles are editable on the map as a whole — translate + resize — but
their polygon approximation's boundary vertices are locked.**
TerraDraw's select-mode `flags` are keyed by the feature's
`properties.mode`; the renderer registers flags for `circle` as
`{ feature: { draggable: true, scaleable: true } }`, with no
`coordinates` entry, so the user can:
- drag the whole circle to move its centre,
- hold `Ctrl+S` and drag to scale (resize the radius),
- but cannot grab individual boundary vertices.

On drag/scale end, the renderer recomputes `center = centroid(ring)` and
`radiusMeters = averageRadiusMeters(center, ring)` from the live polygon
approximation and regenerates a fresh 64-segment canonical polygon via
`updateCircle(id, { center, radiusMeters })`. The dragged approximation
snaps back to the clean circle, preserving the semantic invariant: the
polygon is always a fixed function of `(center, radiusMeters)`. The
renderer's `change` handler additionally skips live writes for circle
features during a drag (only the `finish` event mutates engine state),
so partial drags don't pollute the semantic circle.

## `<RunPanel>` — the run button + cancel + progress

```tsx
export interface RunPanelProps {
  className?: string;  // defaults to 'run-panel'
}
```

- Reads `useRun()` → `{ status, progress, error, run, cancel }`.
- Run button shows:
  - `Run model` when `idle` or any terminal status;
  - `Preparing…` while `preprocessing`, `Submitting…` while `submitting`,
    `Running…` while `running`;
  - a **sliding-hash overlay** (`.btn-run__overlay`) over the button while
    active — the diagonal-stripe keyframes live in the consuming app's
    stylesheet (the demo ships `@keyframes hashSlide`).
- Cancel button appears alongside while active.
- Inline progress bar (`.run-progress` / `.run-progress__bar`) animates
  when `progress.fraction` is set; indeterminate ripple when `null`.
- Failures surface as an inline `.run-error` line.

Stable class names: `.run-panel`, `.btn-run-row`, `.btn-run`,
`.btn-run--{idle|preprocessing|submitting|running|succeeded|failed|cancelled}`,
`.btn-run--visible`, `.btn-run__label`, `.btn-run__overlay`, `.btn-cancel`,
`.run-progress`, `.run-progress__bar`, `.run-error`.

## `<ResultsPanel>` — run history with show/hide on map

```tsx
export interface ResultsPanelProps {
  className?: string;  // defaults to 'results-panel'
}
```

- Reads `useResults()` → `{ summaries, current, showResult, hideResult,
  toggleResult, clearResult, clearAll }`.
- Newest-first `<ul>` of run summaries. Each row shows model id + timestamp
  + status badge.
- Per-row controls:
  - **Show on map / Hide on map** (`run-item__toggle`) — toggles
    `engine.showResult(runId)` / `hideResult(runId)`. The renderer's
    `ResultLayerActions` adds/removes the layer.
  - **✕ dismiss** (`run-item__clear`) — `engine.clearResult(runId)`.
- Toolbar: **Clear all** (`engine.clearAllResults()`).
- Empty state: `.results-empty`.

Stable class names: `.results-panel`, `.results-panel__header`,
`.run-list`, `.run-item`, `.run-item--{succeeded|failed|cancelled|visible}`,
`.run-item__head`, `__name`, `__status`, `__error`, `__actions`,
`.run-item__toggle`, `.run-item__clear`, `.results-empty`.

The engine stores `RunResult = unknown` opaquely; `<ResultsPanel>` does not
interpret it. The renderer narrows via `MapLayerEnvelope.kind` and the dev's
domain-specific summary data (e.g. statistical outputs) is not shown here
yet — a future per-app rich result renderer can plug into the row via a prop
to display summary numbers.

## Per-kind geometry inspector

`<FeatureList>` renders one `<FeatureCard>` per drawn feature. Each card
has a `▸` disclosure on the right of the row that expands to reveal a
`GeometryKind`-specific float editor:

| Kind | Editor fields |
| --- | --- |
| `point` | `lng`, `lat` |
| `circle` | `center lng`, `center lat`, `radius (m)` |
| `linestring` | ordered `[lng, lat]` rows, each editable, plus `+ vertex` / `✕ remove` |
| `polygon` | same, for the outer ring; the closing duplicate vertex is hidden |

Every input is `type="number" step="any"` so exact float positions can be
typed in. Edits flow through engine helpers — `updatePointPosition`,
`updateCircle`, `updateLineStringCoords`, `updatePolygonRing` — that
mutate `feature.geojson` (and `feature.circle` for circles) and push the
new geometry to the renderer (`updateFeatureGeometry`). On-map edits via
TerraDraw select-mode (linestring / polygon) flow the other way and stay
in sync via the renderer's `change` handler.

## Styling — the engine ships no CSS

Components emit **stable class names** (e.g. `draw-toolbar`, `draw-btn`,
`data-feature-item`, `panel-section`, `map-wrapper`, `map-view`). Consumers
either:

- vendor [`apps/demo-web/src/styles/index.css`](https://github.com/anomalyco/catshark-engine/tree/main/apps/demo-web/src/styles/index.css) — it is the **reference stylesheet** and is kept in sync with the class names emitted here, or
- write their own CSS targeting the same class names, or
- override individual components' `className` prop (each accepts an
  optional override so a domain app can rename classes and ship its own
  stylesheet without forking the components themselves).

## Arrangement — the consumer's job

A domain app owns:

1. **Styling** — the CSS, vendored or bespoke.
2. **Arrangement** — composing `<MapScene>`, `<DrawToolbar>`, `<ModelForm>`,
   `<FeatureList>` into its own `<App>` / `<SidePanel>` / section chrome.
3. **Simulation workflow logic** — the `ModelDef`s it `registerModel(…)`s.
   The engine runs them; `<ModelForm>` is generic over any registered model.

`<MapScene>` only owns the overlay-positioning idiom (a relatively-positioned
wrapper around `<Canvas>`). The renderer instance and tile style remain
domain-supplied via the `renderer` prop — so a 3D/WebGPU renderer can drop in
without touching the scene.

## What's deliberately **not** here

- Simulation logic. Lives in `@catshark/core`.
- Rendering backend. Lives in `@catshark/renderer-*`.
- Tile URL strings / network. Lives in `@catshark/client`.
- Result / post-run visualisation. Belongs to future frontend
  functionality (e.g. WebGL result overlays); a domain app would compose
  it as another `<SidePanel>` section reading the same `useModel()` state
  once the engine exposes a result slice.

If a component here starts needing to *compute* rather than *display*,
that logic belongs in `core`; if it starts needing maplibre/WebGL/map URLs,
that belongs in renderer/client. The presentational layer is the only
place layout-over-engine-state chrome belongs.
